Parsing Word, CSV, Excel, JSON, and SQL Data for Retrieval-Augmented Generation (RAG)

Sangitapokhrel
18 min read
·
Nov 23, 2025

--

Retrieval-Augmented Generation (RAG) systems enhance LLMs by feeding them external data, but that data often lives in varied formats like Word documents, spreadsheets, JSON APIs, or databases. Before an LLM can use this knowledge, we need to parse and prepare those files into a chunked, metadata-rich text format that’s easy to embed and retrieve. In this post, we’ll walk through how to ingest real-world data sources (DOCX, CSV, XLSX, JSON, SQL) into a RAG pipeline. We have already written about Pdf Files. We’ll cover why parsing is critical, tackle format-specific challenges, demo 2–3 Python tools for each (including LangChain & LlamaIndex loaders), and show code snippets (with outputs) along the way. We’ll also discuss best practices for chunking and metadata, common pitfalls (like flattening nested JSON or parsing tables), and how to integrate the processed data into a RAG workflow. By the end, you’ll have both an in-depth understanding and a concise summary cheat-sheet for parsing these common file types for RAG.

Why File Parsing is Essential in RAG Pipelines

In a RAG pipeline, document loaders (parsers) are the foundation, they take files in various formats and convert them into plain text that an LLM can work with. If data isn’t loaded and cleaned properly, the AI may miss key information or return wrong answers. Real-world files can be messy (e.g. a DOCX with complex formatting or a CSV with inconsistent entries), so robust parsing ensures we extract useful content and structure while discarding noise. Key reasons to prioritize parsing include:

In short, parsing is the first step that organizes a “messy desk” of data so your AI assistant can find what it needs. Below is a typical ingestion flow in a RAG pipeline:

Ingestion stage of a RAG pipeline: raw data from various sources (documents, databases, etc.) is parsed and cleaned into text, then split into chunks with metadata and embedded into a vector store for semantic search.

  • File ➔ Parsing: Extract text and structure from the source file (e.g. DOCX, CSV).
  • Cleaning ➔ Chunking: Remove noise (formatting, irrelevant text), then break the text into manageable chunks (e.g. paragraphs or rows) for embedding.
  • Embedding ➔ Vector Store: Convert each chunk into an embedding vector and store it along with metadata. This vector database enables semantic retrieval of relevant chunks at query time.

With the overall pipeline in mind, let’s dive into format-specific techniques and tools.

1. Parsing Word Documents (DOCX)

Word documents often contain knowledge bases, policies, reports, or other unstructured text that we want to query in a RAG application. For example, a company might have manuals or FAQs in .docx files that an internal QA bot should leverage.

DOCX files can have complex formatting, headings, lists, tables, footnotes, images, which purely textual extraction might flatten or omit. Important context (like a heading title) could be lost if not handled. Ensuring that all textual content (including headers/footers or text in tables) is extracted is key. We also need to watch out for artifacts like soft hyphens or special characters. Another challenge is dividing the content logically (e.g. by paragraphs or sections) for chunking.

Tools & Libraries: Several Python libraries can extract text from Word documents, each with pros/cons:

  1. python-docx: A popular library to read and write DOCX files. It gives structured access to document elements (paragraphs, runs, tables).

Pros: Can selectively extract or iterate through content (paragraph by paragraph), preserve some structure, and doesn’t require Word to be installed.

Cons: Requires a couple dependencies (e.g. lxml) and by default only pulls main body text, headers, footers, and some list formatting might be missed unless you handle them separately. It also doesn’t extract images (only text).

2. docx2txt: A lightweight, pure-python utility specifically for extracting text (and images) from .docx.

Pros: Very easy to use (essentially one function call), and it captures links, headers, footers, and even images (images are saved separately). It tends to concatenate all text into a single string.

Cons: Loses fine-grained structure, e.g. all paragraphs get joined (with newlines), and you can’t easily tell a heading from body text except by formatting cues. Numbered or bulleted lists may lose their numbering or indentation.

3. LangChain Document Loaders (Word): LangChain provides loaders like Docx2txtLoader and UnstructuredWordDocumentLoader for Word files

Pros: These integrate with RAG pipelines out-of-the-box, returning Document objects with text and metadata. The Unstructured loader uses the Unstructured library to chunk the document into elements (paragraphs, titles, etc.) if desired. This can preserve more structure, e.g. you can get a list of elements like “Title: …” and “Paragraph: …” instead of one blob.

Cons: The Unstructured approach has external dependencies and can be heavy. If used in “single” mode, it will output a single text like docx2txt (no column/row context). Additional setup may be needed for Unstructured. If using Docx2txtLoader, it shares the same limitations as docx2txt discussed above.

Example: Using python-docx: Below we use python-docx to read a .docx and print the combined text of all paragraphs:

from docx import Document

doc = Document("example.docx")  # Load the Word file
full_text = "\n".join(paragraph.text for paragraph in doc.paragraphs)
print(full_text[:100])  # Print first 100 characters
# Output (example): "ACME Corp Policy Handbook\nIntroduction\nACME Corp is committed to ... "

Pros: We can access each paragraph (paragraph.text) and handle them as needed (e.g., keep headings separate or inspect doc.tables).

Cons: By default this misses header/footer text and text inside tables. We’d have to manually extract those (e.g., doc.sections[0].header or iterate doc.tables), which complicates things.

Example: Using docx2txt: With docx2txt, extracting all text is straightforward:

import docx2txt

text = docx2txt.process("example.docx")
print(text[:100])
# Output (example): "ACME Corp Policy Handbook\nIntroduction\nACME Corp is committed to ... [image1.png] ... "

This returns the full document text in one string. You might see placeholders for images (e.g. “[image1.png]”) and all content (headers, footers) in sequence. It’s great for quick ingestion, indeed, “python-docx2txt… can also extract text from links, headers and footers… and images.

Example: Using LangChain Loader: If you’re using LangChain, you can load a Word document directly into Documents:

from langchain.document_loaders import Docx2txtLoader
loader = Docx2txtLoader("example.docx")
docs = loader.load()
print(docs[0].page_content[:100])
# Output: "ACME Corp Policy Handbook\nIntroduction\nACME Corp is committed to ... "

LangChain’s loader above just wraps docx2txt (as shown by the identical output). Alternatively, using the Unstructured loader:

from langchain.document_loaders import UnstructuredWordDocumentLoader
docs = UnstructuredWordDocumentLoader("example.docx", mode="elements").load()
print(len(docs), "elements")
# Output (example): 10 elements
print(docs[0].page_content)  
# e.g., "ACME Corp Policy Handbook"  (first element, perhaps a title)

With mode="elements", you would get a list of document chunks – each might be a title, a paragraph, etc., instead of one big text. Each chunk comes with metadata like category (e.g. “Title” or “Paragraph”) and possibly language or other info. This is useful if you want to preserve that a line was a heading (you could store that in metadata, or use it in chunk text). The trade-off is an extra step to recombine or handle multiple chunks, whereas the “single” mode (or Docx2txtLoader) gives one document.

2. Parsing CSV Files

CSV (Comma-Separated Values) files are essentially tables of data. They appear everywhere, exports from databases or spreadsheets, lists of records (e.g. product catalogs, user lists), survey results, etc. In RAG, CSVs can provide structured facts that an LLM can retrieve. For example, you might have a CSV of employee information, and you want the RAG system to answer “Who is the manager of the Sales department?” by looking up that table.

Challenges: CSVs are simpler than Word docs, but they pose their own issues. A CSV might have dozens of columns, some of which aren’t relevant or are hard to interpret out of context. Data types can vary (dates, numbers, text) and might need formatting. Parsing pitfalls include fields containing commas or newlines (which can break naive split logic, though the CSV format handles it if properly read with a library). Also, very large CSVs (thousands of rows) are problematic to embed in entirety, you may need to filter or chunk them. Another consideration: a single row on its own might be meaningless unless we include the column names as context. For instance, a row “Alice, 30, Engineering” needs headers (“Name: Alice, Age: 30, Department: Engineering”) to make sense to the LLM.

Tools and Libraries

  • csv module (built-in):
    Lightweight, no installation needed, can stream large files line-by-line. But it’s low-level, so you must manually loop and format rows
  • pandas:
    Reads CSVs into DataFrames easily (pd.read_csv). Great for data cleaning, filtering, and handling missing values. But large files can use a lot of memory, and you still need to format output yourself.
  • LangChain CSVLoader:
    Automatically converts each row into a Document object with “column: value” text, ideal for RAG pipelines. But it treats each row separately and loads the whole file (via pandas), so huge files may need custom chunking.
  • Other options:
    You can load CSVs with pandas and feed them into frameworks like LlamaIndex. For very large datasets, tools like Apache Arrow or Dask exist but aren’t needed for most standard use cases.
  • Additionally, if you are using frameworks like LlamaIndex, you might just use pandas to read CSV then feed it to LlamaIndex’s ingestion utilities (like creating documents or using a SimpleDirectoryReader on the file — which might just treat it as text). There’s also Apache Arrow or Dask for big data, but for beginner/mid-level scope, the above tools suffice.

Example: Using csv module: Here’s how to read a CSV and turn each row into a text string:

import csv

with open("employees.csv", newline='') as f:
    reader = csv.DictReader(f)  # reads header row as field names
    for row in reader:
        text = " | ".join(f"{key}: {value}" for key, value in row.items())
        print(text)
        break  # print only the first row for demo
# Output (example): "Name: Alice | Age: 30 | Department: Engineering"

In this snippet, csv.DictReader gives each row as a dict mapping column names to values, then we join them into a single line. We use " | " as a separator for clarity (commas could be confused with the CSV delimiter itself). The output shows the first row with each column labeled. This is exactly the context an LLM needs – documents like these give the LLM the context to understand the meaning behind data (column labels with values). Without the keys, “Alice 30 Engineering” might confuse the model.

Example — Using pandas: We can achieve something similar (all rows as text) with pandas:

import pandas as pd

df = pd.read_csv("employees.csv")
for i, row in df.iterrows():
    text = " | ".join(f"{col}: {row[col]}" for col in df.columns)
    print(text)
    break  # first row for demo
# Output: "Name: Alice | Age: 30 | Department: Engineering"

This produces the same result. Pandas also has a convenient df.to_string() method to get a pretty-printed table in text form, but that tends to align columns in fixed widths. For RAG, it’s usually better to have the “Column: Value” format as above, so that if a chunk is retrieved, the model clearly sees the field labels (even if spacing is lost). We could also use df.to_dict(orient="records") to get a list of dictionaries and then format similarly.

If the CSV is large and you don’t want to load all at once, you can iterate in chunks with pandas (pd.read_csv(..., chunksize=1000)) or stream with the csv module as shown. Consider filtering or selecting only relevant columns before converting to text (e.g. if some columns are irrelevant or highly numeric, maybe exclude them to save token space).

Example: Using LangChain CSVLoader: With LangChain, it’s very straightforward:

from langchain.document_loaders import CSVLoader

loader = CSVLoader(file_path="employees.csv")
docs = loader.load()
print(docs[0].page_content)
# Output: "Name: Alice, Age: 30, Department: Engineering"

By default, each docs[i] corresponds to one CSV row. The content is a comma-separated string of Column: Value pairs (notice it used commas and newline or space as separator – the exact format may be ", " between pairs as above). The loader also automatically includes the CSV file path in metadata, and you can specify parameters like source_column to use a particular column as the Document.metadata['source'] (for instance, using an “ID” or name column as the source label).

3. Parsing Excel Files (XLSX)

Excel files often contain multi-sheet business data, tables, reports, summaries, and charts, that you may want to query in a RAG system.

Challenges:

  • Multiple sheets: Treat each sheet separately and keep sheet names in metadata.
  • Complex layout: Merged cells, formulas, and mixed sections don’t convert cleanly to text.
  • Large size: Slow to read; must chunk by rows or sections.
  • Losing structure: If not labeled properly, cell values lose column/row context.

Tools and Libraries

  • pandas + openpyxl: Best for sheets that behave like tables; easy to load per sheet. Doesn’t preserve formatting and may show NaNs for merged areas.
  • openpyxl (direct): More control when you need to inspect merged cells or unusual layouts.
  • LangChain Excel loaders:

-UnstructuredExcelLoader: Easy, but may output flattened text with little structure.

  • StructuredExcelLoader (community): Preserves exact sheet structure with cell labels (A1, B1, etc.)great for accuracy but verbose.
  • Example: Using pandas: Suppose we have an Excel file with two sheets: “Employees” and “Departments” as in the earlier example. We’ll load each sheet and output rows similarly to CSV:
import pandas as pd

xls = pd.ExcelFile("company_data.xlsx")
for sheet_name in xls.sheet_names:
    df = pd.read_excel(xls, sheet_name=sheet_name)
    for _, row in df.iterrows():
        text = " | ".join(f"{col}: {row[col]}" for col in df.columns)
        print(f"[{sheet_name}] " + text)
    break  # demo: break after first sheet for brevity
# Output example:
# [Employees] Name: John Doe | Department: Sales | Salary: 50000
# [Employees] Name: Jane Smith | Department: Marketing | Salary: 55000

Here we prefixed the text with the sheet name in brackets for clarity. The output shows two rows from the “Employees” sheet, each labeled with headers. We would do the same for “Departments”. In practice, you might want to keep each sheet’s data separate (e.g., treat “Employees” records and “Departments” records as different sets, since queries might be specific). Attaching the sheet name either in the text or at least in metadata ({"sheet": "Employees"}) is important for context. For instance, if a user asks “What is the salary of Jane Smith?”, the chunk with “Name: Jane Smith | ... Salary: 55000” is relevant – and we know it’s from the Employees sheet.

Example: LangChain UnstructuredExcelLoader: Using the unstructured loader in element mode:

from langchain.document_loaders import UnstructuredExcelLoader

loader = UnstructuredExcelLoader("company_data.xlsx", mode="elements")
docs = loader.load()
print(len(docs), "documents loaded")
# Output: e.g. "4 documents loaded"
for d in docs:
    print(d.metadata.get("page_name"), d.metadata.get("category"))
# Possible output:
# "Employees" Title
# "Employees" Table
# "Departments" Title
# "Departments" Table

As this hypothetical output suggests, the loader might produce a document for the sheet title and one for the sheet’s table content for each sheet. Each doc’s page_name metadata holds the sheet name, and category might be 'Title' or 'Table'. The page_content of the 'Table' docs would be the textual table (likely with columns and rows separated by newlines). For example, docs[1].page_content might contain something like:

Team  Location  Stanley Cups  
Blues STL       1  
Flyers PHI      2  
Maple Leafs TOR 13

Example: StructuredExcelLoader output: To illustrate the structured approach, here’s an example output for a tiny spreadsheet from the StructuredExcelLoader docs:

SHEET: "Employees"

ROW 1:
CELL A1: Name
CELL B1: Department
CELL C1: Salary

ROW 2:
CELL A2: John Doe
CELL B2: Sales
CELL C2: 50000

ROW 3:
CELL A3: Jane Smith
CELL B3: Marketing
CELL C3: 55000

Example of structured text output for an Excel sheet, preserving cell positions. Each sheet becomes a document with every cell labeled. An LLM reading this would clearly know, for instance, that “John Doe” is in the Name column (A2 corresponds to Name header at A1). The downside is that it’s quite verbose, imagine 100 rows of this. It can blow up the token count. In many cases, a slightly less granular approach (like just “Name: John Doe, Department: Sales, Salary: 50000”) is sufficient. Nonetheless, this approach is useful if relative positions or multiple tables need to be distinguished.

Best Practices:

  • Treat each sheet separately:
    Store sheet name in metadata so context isn’t lost.
  • Always include headers:
    Keep column names with each row. If a sheet has no clear headers, create your own labels.
  • Skip non-useful content:
    Ignore empty sheets, notes, charts, or irrelevant cells.
  • Use metadata wisely:
    Include file name, sheet name, and optional row/cell info for traceability.
  • Chunk sensibly:
    For table-like sheets, use one row per chunk. For narrative or mixed layouts, chunk by logical sections (e.g., a text block, a table, etc.).
  • Watch out for pitfalls:
  • Merged cells → fill down or add context manually.
  • Hidden sheets → exclude if not needed.
  • Formulas → you get stored values, which is usually fine.
  • Optional: Convert simple sheets to CSV for easier ingestion.

4. Parsing JSON Data

JSON is common for structured/semi-structured data (APIs, product info, logs, FAQs, nested categories). In RAG, you may need to turn JSON objects into readable text chunks.

Key Challenges:

  • Nested structure: Needs flattening, raw JSON is hard for LLMs.
  • Deciding what to index: Skip irrelevant fields (IDs, flags).
  • Large files: Break into smaller documents; use streaming for huge JSON.
  • Maintaining context: Always include key names so values aren’t ambiguous.

Tools & Approaches:

  • Python json module: Simple and flexible; you manually extract needed fields.
  • pandas (json_normalize): Quick flattening for record-like JSON.
  • LangChain JSONLoader: Pulls specific elements using JQ; gives one Document per JSON element.
  • Custom flattening: Useful for irregular or deeply nested structures.

Example: Using JSONLoader (LangChain): Suppose we have a JSON file products.json with content: {"products": [ {"id": 1, "name": "Widget", "price": 25, "details": {"color": "red", "in_stock": true}}, {...} ] }. We want each product as a document:

from langchain.document_loaders import JSONLoader

loader = JSONLoader(file_path="products.json", jq_schema=".products[]")
docs = loader.load()
print(docs[0].page_content)
# Output (example): '{"id": 1, "name": "Widget", "price": 25, "details": {"color": "red", "in_stock": true}}'

Now docs[0] contains the JSON string for the first product. This is fine but for better LLM utilization, we might transform that content. For instance, we could post-process each docs[i].page_content by loading it back to Python dict and formatting as a nicer text. Alternatively, we could have provided text_content=False when loading (so that it keeps it as Python objects in metadata), but it’s easier to just manually format:

import json
record = json.loads(docs[0].page_content)
text = f'Name: {record["name"]}\nPrice: ${record["price"]}\nColor: {record["details"]["color"]}\nIn stock: {record["details"]["in_stock"]}'
docs[0].page_content = text
print(docs[0].page_content)
# Output:
# Name: Widget
# Price: $25
# Color: red
# In stock: True

This yields a human-friendly text representation of the JSON object. We incorporated nested fields (details.color etc.) into key: value lines. You would do this for each doc. This manual step is needed because, as noted, “complex or nested JSON needs careful [extraction] to get the right data” – an automated loader might not present it in the ideal way for an LLM.

Example: Custom parsing with Python json: Without LangChain, you could do:

import json

with open("products.json") as f:
    data = json.load(f)
documents = []
for item in data["products"]:
    text = f'Name: {item["name"]}, Price: ${item["price"]}, Color: {item["details"]["color"]}, In stock: {item["details"]["in_stock"]}'
    documents.append(text)
    print(text)
    break  # first item
# Output: "Name: Widget, Price: $25, Color: red, In stock: True"

This is straightforward since we knew the structure (a list under “products”). If the JSON were more irregular, we might need to recursively iterate. Another scenario: JSON Lines (.jsonl), where each line is a JSON object. In that case, you can read line by line and parse each to an object, treating each as a record.

Best Practices:

  • One document per logical item: e.g., each object in a list = one chunk.
  • Flatten nested fields: Make all important values explicit (e.g., education.college: X University).
  • Readable lists: Convert arrays into clear comma-separated or bulleted lists.
  • Use metadata: File name, IDs, categories, or paths.
  • Chunk long text fields: If text inside JSON is very long, split it but keep object metadata.

5. Parsing SQL Databases

Use SQL data in RAG by exporting table rows as readable text chunks. Useful for customer records, products, transactions, etc. SQL dump files (.sql) need to be restored or parsed before extracting data.

Key Challenges:

  • Relational links: Data is in multiple tables; foreign keys need joining to produce meaningful text (e.g., show “Engineering” instead of dept_id=5).
  • Large volume: Databases can be huge, avoid embedding massive tables; focus on important/semantic fields.
  • Stale data: Static embeddings get outdated when DB updates.
  • Dump files: Must restore or parse INSERT statements; they’re not data-ready.

Tools:

  • sqlite3 / DB connectors / SQLAlchemy: Run SELECT queries and fetch rows.
  • pandas.read_sql: Good for DataFrame workflows
  • LlamaIndex DatabaseReader / LangChain SQL tools: Mostly for dynamic queries, but can also pull tables for indexing.

Example: Using SQLite (Python): Let’s say we have a SQLite database company.db with an employees table.

import sqlite3

conn = sqlite3.connect("company.db")
cursor = conn.cursor()
cursor.execute("SELECT name, age, department FROM employees;")
rows = cursor.fetchall()
for row in rows[:2]:
    text = f"Name: {row[0]}, Age: {row[1]}, Department: {row[2]}"
    print(text)
# Output (example):
# Name: Alice, Age: 30, Department: Engineering
# Name: Bob, Age: 25, Department: Sales

This prints two example rows as text. In practice, you’d loop all rows and create Document chunks similarly. If the table had foreign keys (e.g., department was an ID referencing a departments table), you have a choice: do a join in the SQL query to get the actual name (preferred), or index the ID (less useful for natural questions). It’s usually better to join and have human-readable info in the text chunk. For example, use SELECT e.name, e.age, d.dept_name FROM employees e JOIN departments d ON e.dept_id = d.id; so that the chunk contains "Department: Engineering" instead of "Department: 5".

If connecting to a different database (say PostgreSQL), you’d use that DB’s connector or an SQLAlchemy engine in place of the sqlite3 connection, but the concept remains: execute a SELECT, get rows.

Example: Creating Documents from SQL with LangChain/LlamaIndex: While not demonstrating full code, here’s a conceptual flow:

  • Use LangChain’s CSVLoader or DataFrameLoader after pulling data from SQL. For instance, if rows is a list of tuples as above, you could turn it into a DataFrame df = pd.DataFrame(rows, columns=["Name","Age","Department"]) and then do docs = DataFrameLoader(df).load(). This would yield docs like "Name: Alice\nAge: 30\nDepartment: Engineering" for each row (assuming DataFrameLoader splits by row with one doc per row).
  • LlamaIndex’s DatabaseReader could be invoked as:
from llama_hub import SimpleDatabaseReader
reader = SimpleDatabaseReader(sql_url="sqlite:///company.db")
documents = reader.load_data(table_names=["employees"])
  • This might return the entire table content as one or multiple Document nodes (depending on implementation). You’d likely still need to chunk them.

For direct RAG indexing, manual control is usually fine.

Final Project Using LangChain and LlamaIndex

After parsing and chunking the data from Word, CSV, Excel, JSON, and SQL sources, the next steps are embedding these chunks and using them in an LLM chain for question answering. The high-level process is similar regardless of source: you have a list of text chunks (with metadata) that represent your knowledge base. You embed each chunk into a vector store. Then, at query time, you embed the query, find similar chunks, and feed them (plus possibly their metadata) into the LLM prompt.

Let’s outline integration using two popular frameworks: LangChain and LlamaIndex.

Using LangChain: LangChain makes it easy to go from documents to answers:

  1. Load documents: Use the Document Loaders we discussed (or your own code) to get a list of Document objects. For example, docs = CSVLoader("employees.csv").load() or for a custom parse, you’d create Document(page_content=text, metadata=meta) for each chunk.

2. Split documents (if not already chunked): For sources like Word docs or long text fields, you may need to chunk further. LangChain provides text splitters such as RecursiveCharacterTextSplitter which splits by tokens/characters (honoring sentence boundaries, etc.), or MarkdownHeaderTextSplitter if you have structured text with headings. For our cases, we mostly already chunked by row/paragraph, so a splitter might not be needed except for very large paragraphs.

from langchain.text_splitter import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
split_docs = splitter.split_documents(docs)

If docs are already small (like one row each), this will either leave them as is or break any that exceed 500 characters.

3. Embed and store: Choose an embedding model (e.g., OpenAI’s text-embedding-ada-002 via OpenAIEmbeddings, or Cohere, etc.) and a vector store (FAISS for local in-memory, or Pinecone/Chroma for more persistent storage).

from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import FAISS

embeddings = OpenAIEmbeddings()  # assumes API key is set
vector_store = FAISS.from_documents(split_docs, embedding=embeddings)

This generates embeddings for each document chunk and stores them in a FAISS index. Metadata from the Document objects will be kept alongside vectors.

4. Build Retrieval QA chain: LangChain offers RetrievalQA or similar chain that wraps the retrieval + LLM call.

from langchain.llms import OpenAI
from langchain.chains import RetrievalQA
qa_chain = RetrievalQA.from_chain_type(llm=OpenAI(), chain_type="stuff", retriever=vector_store.as_retriever())

Here, .as_retriever() gives a retriever interface for the vector store (with default top-k settings, etc.). chain_type="stuff" means it will stuff all retrieved chunks into the prompt (there are other options like map-reduce, refine, but “stuff” is straightforward for smaller numbers of docs).

5. Ask questions:

query = "Who is the manager of the Engineering department?"
result = qa_chain.run(query)
print(result)
# Output (example): "The manager of the Engineering department is Alice."

The chain will embed the query, find relevant chunks (e.g., maybe the “Department: Engineering, Manager: Alice” row from a CSV or JSON we indexed), and then the LLM composes the answer using that context.

The above pipeline would work similarly regardless of the original file type, because by this point, everything is just chunks of text in the vector store. The main difference format-to-format is how you parse and chunk.

Using LlamaIndex (GPT Index): LlamaIndex provides a slightly different abstraction. You would:

  1. Create Documents/Nodes: Use LlamaIndex’s readers or just manually create Document objects from text. For example:
from llama_index import Document, VectorStoreIndex, StorageContext
documents = [Document(text_chunk, metadata=meta) for text_chunk, meta in list_of_chunks]

2. Construct an index:

index = VectorStoreIndex.from_documents(documents)

By default this will use a default embeddings model (often OpenAI) and a default vector store (in-memory). You can configure it to use external vector DBs like Qdrant, Chroma, etc., by providing a StorageContext with the desired VectorStore.

3. Query the index:

query_engine = index.as_query_engine()
response = query_engine.query("Who is the manager of the Engineering department?")
print(response)
# Output: "The manager of the Engineering department is Alice."

LlamaIndex will retrieve relevant nodes and by default synthesize an answer (it does a similar stuffing of context and uses an LLM to generate a response). LlamaIndex also supports more complex query types, e.g., you could do a structured query against the index or get source citations easily.
